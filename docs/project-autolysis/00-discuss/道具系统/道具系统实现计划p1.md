# 道具系统第一部分实现计划

编写日期：2026年9月25日。

本计划依据[道具系统讨论文档](/D:/autolysis/docs/project-autolysis/00-discuss/道具系统/道具系统讨论p1.md)及[道具系统术语](/D:/autolysis/docs/project-autolysis/00-discuss/道具系统/CONTEXT.md)，覆盖用户已经确认的道具栏、手持显示、两种原药、原药组和原药放置架。

状态：已实施并完成本期验证，完成日期为2026年9月25日。实际改动、运行结果、连续原生报错的处理及证据见[实施记录](/D:/autolysis/docs/project-autolysis/00-discuss/道具系统/道具系统p1实施记录.md)。下文保留设计约束及实施前核查依据；其中旧场景现状用于说明改动原因，不能解释为当前仍缺少实现。实施前未提交修改已保留并完成基线对比。

## 一、目标与完成条件

### 1. 已确认行为

| 编号 | 必须实现的行为 |
| --- | --- |
| 需求一 | 初始4格、全部为空；每格一个道具，不叠加；默认聚焦第一格。 |
| 需求二 | 单格80×80像素，间距10像素；使用参考格子资源与聚焦效果；水平方向居中，下边缘距底端80像素，设计分辨率1920×1080。 |
| 需求三 | 滚轮向下选下一格，向上选上一格，两端循环。 |
| 需求四 | 当前聚焦格决定空手或手持；切换不丢失其他格道具；有道具时显示对应手持模型。 |
| 需求五 | 空手交互原药组，获得一个对应原药，进入当前格；组内陈列不减少。当前格已有道具时不自动寻找其他空格。 |
| 需求六 | 原药组外的独立原药可以直接交互取走；架上取回必须瞄准具体原药。 |
| 需求七 | 手持原药交互架体，放入编号最小的空槽位；满架不接受；成功放入后当前格为空，聚焦不变。 |
| 需求八 | 两种原药可以混放，共用所有槽位；取回后释放原槽位。 |
| 需求九 | 道具栏在正常游戏过程中持续显示于屏幕下方，进入游戏即显示全部4格；无需额外按键唤出，空栏或一段时间未操作时也不自动隐藏。 |

完成条件：上述行为在实际玩家、实际两类原药组和实际放置架之间连通；行为测试、现有相关回归、实际渲染和主场景操作均有证据。必须验证准星、格子内容、手持显示与架上占用一致。无图形测试通过不等于画面或完整输入验证通过。

### 2. 范围

本期不加入叠加、拖拽整理、物品使用、丢弃、数字键切换、道具栏扩容、存读档或跨场景持久化。保持原有玩家移动、脚步、摄像机层级、直接交互按键、2单位射线距离及首个碰撞规则。

参考项目仅读取；新项目只迁入所需视觉与音频资产，不引入参考背包、全局音频管理器或存档依赖。现有两个原药架实例分别维护自身占用。

道具栏作为常驻游戏界面随玩家界面初始化，持续显示格子及当前聚焦状态。输入配置只增加上一格、下一格切换，不增加道具栏打开、关闭或显示切换动作。

## 四、模块与接口设计

### 1. 数据归属

- 道具定义使用 AutolysisItemDefinition（自溶道具定义资源）：记录稳定类型标识、中文名称、原药类别、图标、纯显示场景、世界场景路径和手持局部变换。两种原药各一份定义；运行时只读。
- 道具栏控制器 AutolysisInventoryController（自溶道具栏控制器）持有长度4的私有道具定义数组及一个聚焦索引。每个非空元素代表一个实体道具；重复引用同一种定义不表示叠加。没有数量字段，也不把占用状态写入共享资源。
- 独立世界原药脚本 AutolysisRawMaterial（自溶原药物体）持有一个道具定义，以及可选的架子归属和槽位编号。一次成功取走只处理被命中的这个世界节点。
- 原药架脚本 AutolysisRawMaterialShelf（自溶原药放置架）持有排序后的槽位节点和对应世界原药引用。原药组脚本只记录产出的道具定义，不维护库存。
- 手持显示与界面只读取道具栏状态；不得另外维护第二份道具数量、当前手持数据或架子占用。

本期没有耐久、剂量等单件可变属性，因此不另建单件属性系统。未来加入这类规则时再扩展，当前先用每格一个定义引用表达占用。

资源依赖约束：纯显示场景不引用道具定义；道具定义以资源保存纯显示场景，以带场景文件筛选的路径字符串保存世界场景地址。世界单体可以引用道具定义，避免“道具定义直接预载世界单体、世界单体又预载道具定义”的循环。实际加载与资源类型检查在转移准备阶段完成。

### 2. 道具栏的最小公开接口

以下名称为拟新增接口，实施时须先检查项目内重名和调用关系。空引用用 null（空值）表示，返回结果用 bool（布尔值）表示；参数和返回值明确类型。

| 拟新增接口 | 契约 |
| --- | --- |
| get_slot_item（读取指定格道具） | 只读返回指定格内容；不暴露可被外部修改的数组。 |
| get_focused_item（读取聚焦格道具） | 唯一手持数据来源；为空即空手。 |
| cycle_focus（循环切换聚焦） | 输入方向仅为前一格或后一格；禁用输入时不调用；事务中拒绝切换。 |
| can_receive_item（能否接收道具） | 检查定义有效、显示资源可用、当前聚焦格为空和没有正在进行的转移；只查询。 |
| try_receive_item（尝试接收道具） | 原药组发放的入口；仅写当前聚焦格，成功一次只放一件。 |
| try_take_world_item（尝试取走世界原药） | 校验指定世界物体，协调当前格、世界节点和可选架子槽位；一次操作完整成功或保持原状。 |
| try_place_on_shelf（尝试放入原药架） | 校验当前原药及目标架子，准备世界实例并协调双方占用，成功后当前格清空。 |

道具栏只发出一次 inventory_changed（道具栏状态已改变）通知，观察者收到时双方状态必须已经一致；界面与手持显示据此读取状态。聚焦索引的只读访问用于界面。初始绑定后主动渲染一次，不能依赖初始信号必然被收到。

道具栏可见性不由上述状态通知或输入许可控制；空栏、空手、切格、取放以及输入暂时禁用都不隐藏整条道具栏。显示常驻道具栏不得将玩家 is_showing_ui（正在显示占用输入的界面）设为真，也不得释放鼠标或暂停移动；[现有交互许可](/D:/autolysis/main-autolysis/player/autolysis_player.gd:143)会依据该字段禁止交互，因此不能把“任意界面可见”与“占用游戏输入的界面已打开”混用。

原药组、单体和架子的交互接收方法只调用上述业务入口。事务的校验、暂存、提交、失败清理由控制器集中组织；架子提供内部槽位查询与登记协作，不另建通用背包转移框架。

### 3. 交互许可扩展

在 AutolysisInteractionComponent（自溶交互组件）增加一个可选业务许可查询，接收 actor（发起者）并返回布尔值，使用 Callable（可调用对象）绑定实际物体方法。未配置查询时，保留现有门与开关行为。

实现约束：

1. 原有启用状态、直接交互模式、存活物理父节点、唯一有效同步单参数接收者检查全部保留。
2. 业务查询不得生成或释放节点、发通知、播放声音、改变格子、占位或切换焦点。
3. 查询已经配置但失效、接收者被释放或返回类型错误时，结果为不可交互；必须区分“从未配置”和“曾配置但已失效”。
4. can_interact（能否交互）合并基础许可与业务许可；try_interact（尝试交互）仍在分发前调用同一检查。
5. 原药组要求可接收到当前空格；单体要求当前格为空且物体未被取走；架子要求当前手持原药且有空位。
6. 保持 interaction_requested（交互请求）唯一同步接收者契约，界面和音效不能再订阅该请求造成第二接收者。
7. try_interact（尝试交互）返回真仍仅表示请求已分发；取放是否成功使用业务入口返回值。

控制器继续只解析首个碰撞物的唯一直接子交互组件。状态变动后通过现有刷新流程更新准星；切格后主动请求刷新，避免等待鼠标移动才更新可用性。

### 4. 转移的提交顺序

每次转移使用控制器内的执行中标记防止重入。保存当前索引和原内容，在提交前再次核对。准备阶段允许失败；提交阶段保持同步，不等待动画或下一帧，不在中间态发通知。

**原药组发放：**验证定义与当前空格 → 准备手持显示所需资源 → 写入当前格 → 发布状态改变。原药组节点与陈列模型完全不变。

**世界原药取回：**验证单体存活及当前格为空 → 若来自架子，验证槽位仍记录该节点 → 准备显示 → 暂停该单体交互 → 同步登记到道具格并解除架子占用 → 隐藏且禁用世界物体碰撞并安排释放 → 发布状态改变。重复点击不得再次接收正在删除的物体。

**放入架子：**验证当前道具为原药 → 获取编号最小的空位 → 加载并在树外准备正确的世界实例 → 复核当前格与目标空位 → 将实例绑定到槽位并完成初始化 → 同步登记占用并清空原格 → 发布状态改变。实例未准备好或登记失败时销毁暂存实例，保留原格内容。

内部节点装配若触发初始化回调，依然由执行中标记阻止再次进入取放；若中途任一已验证对象失效，恢复原占用再结束。显示实例资源缺失属于配置错误，不能先扣掉玩家或世界原药再报告错误。

提交后的不变量：除原药组发放外，玩家所有非空格数与架上原药数之和不变；独立世界原药取回则计入操作前后的世界原药总数。每件架上原药恰属一个槽位，一个槽位最多一件。

4. 独立单体取回成功后取消交互与碰撞，再安排释放；失败时位置、可见性和归属不变。
5. 切格或拾取后刷新准星；有空格但当前格已占用时，组与单体均不可拾取。

完成条件：实际中心射线、左键、组发放、格子与手持完整连通；原药组反复发放后四件陈列始终存在；手持其他道具也不能绕过空格限制。

### 阶段五：36槽位架体与取放

1. 读取既有槽位子节点，按名称中的数字编号排序；不能按字符串排序，避免编号10排在编号2之前。重复或无法解析的编号视为配置错误，报告具体节点，禁止默默选择。
2. 使用读取到的槽位数量作为容量；当前预制体断言36。仅支持一个槽位一件原药；两种原药使用同一占用表。
3. 把原整体盒碰撞替换为与两块层板及背板相符的多个盒形碰撞，全部属于原架体根物理体。保留根旋转、视觉模型和全部槽位变换；架体的实心部分仍遮挡射线并阻挡角色。
4. 放入时选择编号最小空位，准备正确世界单体并绑定槽位，成功后清空当前格。两架各自维护占用，不能污染另一架。
5. 取回时只处理射线命中的原药，其归属槽位同步清空；不因瞄准架体自动取药，也不在手持时自动交换架上原药。
6. 逐槽验证命中：测试视点必须在架外、在交互距离内，不能把射线起点放进盒体伪造可达。相邻原药和层板确实挡住后方原药时保持首个命中规则，通过改变站位取得视线。

完成条件：两种原药各自能经过每个槽位完成放入、瞄准、取回；混放满36后第37次放入失败且玩家道具保留；取走任意原药后按编号补空；实际主场景两个架子可分别完成循环。

## 九、官方依据与适用限制

以下已在编写计划时查阅，用于核对引擎机制，不用于替代用户需求或运行验收。

- 资源按路径缓存，重复加载可能返回共享引用；因此道具定义只读、运行占用归各控制器所有。参见[资源类官方说明](https://docs.godotengine.org/en/4.6/classes/class_resource.html)。
- 界面锚点与偏移用于相对视口定位；已被界面接收的事件不再进入未处理输入回调，忽略鼠标的控件不阻拦点击。参见[界面控件官方说明](https://docs.godotengine.org/en/4.6/classes/class_control.html)。

- 三维节点具有局部和全局变换；本计划通过槽位父子关系保留架体旋转。参见[三维节点官方说明](https://docs.godotengine.org/en/4.6/classes/class_node3d.html)。
- 无图形模式、项目路径与脚本入口按引擎命令行约定使用；脚本入口须继承对应主循环类型。参见[命令行官方说明](https://docs.godotengine.org/en/4.6/tutorials/editor/command_line_tutorial.html)。
